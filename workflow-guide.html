0 · Run it & sign in

The app runs with zero infrastructure. It seeds itself on first launch and signs in with passwordless demo identities.

Start the app

npm install
npm run dev
# open http://localhost:3000

Demo mode is on by default (DEMO_MODE=true), so the sign-in page shows one-click demo personas. Data lives in .data/store.json (in-memory + JSON). To reset to a clean seed, stop the server, delete .data/store.json, and restart.

Two run modes. Everything below works in demo mode. For production the same code runs on Postgres (DATA_DRIVER=prisma) with Microsoft Entra ID SSO (DEMO_MODE=false); see the Reference section for the environment flags.

Intake — creating tickets

Five ways in, one pipeline. All of them classify, set SLAs, route, and run the AI resolver identically.

1

Raise a request via the portal

requester/portal

Requesters search the help center, browse the service catalog, and submit a request. Catalog items can be flagged to require manager approval.

Sign in as Dana Test it
  1. Go to /portal (Raise a Request).
  2. Type a subject like "VPN keeps dropping" and a description, then submit.
  3. Watch the confirmation — it shows the new reference (e.g. INC-…) and status.
  4. Open "My Requests" to see it listed.
Expect: a ticket is created, AI-classified, and either answered instantly (auto-resolved) or marked for follow-up — all without a page reload.
2

Raise a ticket as an agent

agent+/tickets → New ticket

Agents log tickets on behalf of a requester and can set impact/urgency directly (requesters can't — the AI infers those).

Sign in as Arjun Test it
  1. Go to /tickets and click New ticket.
  2. Pick type (incident / service request), category, and set impact + urgency.
  3. Submit and open the created ticket.
Expect: priority is derived from impact × urgency (e.g. High × High → critical), and the ticket lands in the workspace with SLA timers running.
3

Raise via REST API & channels

/api/v1/intakewebhooks

The unified intake endpoint accepts portal/email/chat/API/phone/Teams/monitoring-alert payloads. Provider webhooks (/api/webhooks/{generic,zendesk,freshdesk,slack}), M365 email polling, and a Teams bot all feed the same pipeline. In demo mode you can act as any user with the x-actor header.

Terminal (demo mode) Test it
  1. With the dev server running, send an intake request:
curl -s -X POST http://localhost:3000/api/v1/intake \
  -H "content-type: application/json" \
  -H "x-actor: dana.lee@netlink.com" \
  -d '{"channel":"portal","subject":"New laptop please","body":"My laptop won'\''t boot","requesterEmail":"dana.lee@netlink.com"}'
Expect: a JSON { ok, data } response with the new ticket. A monitoring alert (channel:"alert") instead maps severity → impact×urgency and links the named CMDB item.

AI triage & resolution

The AI is the first responder. It degrades gracefully to deterministic heuristics when no LLM key is set.

4

AI classification & auto-tagging

newautomatic

On intake the AI fills the category, impact, urgency (→ priority), and sentiment when they aren't supplied, and now also suggests topical tags that are merged onto the ticket (alongside any vip/monitoring tags).

Sign in as Arjun Test it
  1. Create a ticket with subject "VPN disconnects and email is slow" (leave category to the AI).
  2. Open the ticket and look at the Tags field in the properties panel.
Expect: a sensible category (Network) and auto-tags such as vpn, network, email. VIP requesters also get a vip tag and an urgency floor.
5

AI resolver — auto-resolve · suggest · escalate

automatic

The resolver retrieves knowledge-base matches (vector search), generates a grounded answer with citations, scores its confidence, and decides:

  • ≥ 0.78 — auto-resolves with a cited reply (P1/critical is never auto-closed).
  • ≥ 0.55 — drafts a suggestion for an agent (status pending_agent).
  • otherwise — escalates for a human.
Sign in as Arjun Test it
  1. Open any open ticket in the agent workspace.
  2. In the composer, click Run AI.
  3. Watch the toast + status change (auto-resolved / draft ready / escalated).
Expect: a grounded reply with source citations appears in the thread, and the status reflects the confidence decision. Open the AI panel to see confidence, reasoning, and cited articles.

Routing & dispatch

Category routing hands each ticket to the right "profile" (assignment group); a human dispatcher assigns the person.

6

Category → group routing (profiles)

Settings → groups

Each category is owned by one specialist "profile" group, plus a generalist Service Desk for the common ones:

  • Access & Identity → Access · Network Operations → Network · Endpoint & Hardware → Hardware · Software & Apps → Software
  • Service Desk (generalist) → IT, Billing, Other · People Operations → HR

Specialist groups use the manual strategy, so intake routes a ticket to the group but leaves it unassigned for the dispatcher.

Sign in as Priya Test it
  1. Create a Hardware ticket ("new laptop").
  2. Open it and check the Assignment group in properties.
Expect: group = Endpoint & Hardware, assignee = empty (waiting for triage). Settings → Assignment groups shows all six profiles and their categories.
7

Triage / dispatch board

newmanager / admin/triage

A dispatcher-only queue of unassigned open tickets. Selecting a ticket shows the eligible people split into Specialists (the ticket's group) and Common (Service Desk), each with a live open-ticket load bar and an Available/Away chip, sorted available-first then lightest-load. A persistent Team-workload panel shows everyone's capacity.

Sign in as Priya (or Meera) Test it
  1. Open Triage from the sidebar (only visible to manager+).
  2. Pick an unassigned ticket from the queue.
  3. Review the specialists' vs common handlers' open-counts and availability.
  4. Click Assign on the lightest-loaded available agent.
Expect: the ticket leaves the queue, the chosen agent's load ticks up, and the ticket now shows that assignee. A requester visiting /triage is redirected/blocked (403 from the API).

Link & merge tickets

newagent+

Relate duplicates/related tickets, or merge a duplicate into a target — merging re-parents the source's messages onto the target, cancels the source, and links them (non-destructive, fully audited).

Sign in as Arjun Test it

  2. Pick another ticket and click Link (both now list each other).
  3. Pick a duplicate and click Merge into…, confirm.

Resolve / close / reopen

agent+ · requester

Agents resolve (optionally with a reply + resolution notes), close, or put a ticket on hold (pending pauses the SLA clock). A requester replying to a resolved ticket reopens it.

Arjun then Dana Test it
  1. As Arjun: on an open ticket, click Submit as Solved with a short reply.
  2. As Dana: open the request and post a reply.
Expect: the ticket resolves and notifies Dana; Dana's reply flips it to reopened and it re-enters the active queue.

SLA & approvals

Deadlines are derived from priority, pause while waiting, and escalate in stages. Catalog requests can require sign-off.

15

SLA timers & staged escalation

background job

Each ticket gets response + resolution deadlines from its priority (P1 15m/2h … P5 8h/5d). At 80% of the window it's tagged sla_at_risk and the assignee/manager are warned; on breach it auto-escalates and alerts go out. pending pauses the clock; leaving pending resumes and shifts the deadlines. Business calendars (timezone/working window/holidays) can be linked per policy.

Sign in as Arjun Test it
  1. Open a ticket and read the SLA panel (First response / Resolution bars + due countdown).
  2. Put it On hold (pending) and note the "Clock paused" badge.
  3. Bring it back to in-progress (send a reply) — the deadlines shift out by the paused time.
Expect: the SLA badge tracks met / at-risk / breached; pausing freezes the countdown; the background sweep tags at-risk and escalates on breach.
16

Service-request approvals

manager decides

Catalog items flagged requiresApproval hold the ticket (SLA paused) with an approval for the manager. Approving resumes fulfilment (routing → automations → AI); rejecting cancels — both notify the requester.

Dana then Meera Test it
  1. As Dana: from the portal catalog, submit an item that requires approval.
  2. As Meera: open the ticket → Approval panel → Approve (or Reject).
Expect: the ticket sits in pending with a "Waiting on {approver}" card and paused SLA; approving resumes the pipeline, rejecting cancels — Dana is notified either way.
17

Requester experience & CSAT

requester

Requesters see only their own tickets, reply in a chat-style thread, and rate the resolution. "Not yet" reopens the ticket.

Sign in as Dana Test it
  1. Open a resolved request; a "Did this resolve your issue?" prompt appears.
  2. Click Yes, resolved or Not yet.
Expect: "Yes" records satisfaction and closes it; "Not yet" reopens it for an agent. CSAT feeds the analytics dashboard.
18

Automations (when / if / then)

adminSettings → Automation rules

Rules trigger on ticket.created, ticket.updated, sla.at_risk, or sla.breached, match ALL/ANY conditions, and run actions (assign / set priority / status / category / add tag / notify / run AI). A dry-run previews what a rule would do without mutating anything.

Sign in as Priya Test it
  1. Settings → Automation rules → New rule.
  2. e.g. when ticket.created, if category = Network, then add tag "net-triage".
  3. Create a Network ticket and check its tags.
Expect: the rule's run-count increments and the action applies (the new tag shows on matching tickets).

Cluster recurring incidents into a Problem, record root-cause (RCA), publish a workaround as a known-error KB article, and raise a Change for the permanent fix. AI can suggest clusters and a root cause.

26

Audit trail

/audit

Every lifecycle step, AI decision, automation, approval, assignment, and sign-in appends a SHA-256 hash-linked block to the per-tenant chain. The verifier recomputes the chain and pinpoints any tampering.

Sign in as Priya Test it
  1. Open /audit and browse recent blocks for a ticket you just worked.
  2. Run the verify action (or hit /api/v1/audit?verify=1).
Expect: the chain verifies as intact; each action you took (assign, reply, resolve, override) is present with actor + payload hash.

A · Testing appendix

Ways to verify the whole system — by hand, via the API, or automated.

In-person happy path (≈10 min) — one continuous run that exercises the core loop:

  1. Dana Raise a request in the portal → note the reference.
  2. Priya Open Triage, assign it to the lightest-loaded available agent.
  3. Arjun Open the ticket, insert a macro, run/adjust the reply, set a custom field, and Submit as Solved.
  4. Dana Reply once (it reopens), then rate Yes, resolved (CSAT).
  5. Priya Open Analytics → Download PDF; open Audit → verify the chain.
Expect: every hop reflects instantly (SSE), SLA + audit track each step, and the analytics/CSAT numbers move.

API testing (demo mode) — act as any user with the x-actor header against /api/v1:

# list unassigned tickets (dispatch queue)
curl -s "http://localhost:3000/api/v1/tickets?assigneeId=unassigned" \
  -H "x-actor: priya.sharma@netlink.com"

# the triage board (manager/admin only)
curl -s http://localhost:3000/api/v1/triage -H "x-actor: meera.nair@netlink.com"

# assign a ticket
curl -s -X POST http://localhost:3000/api/v1/tickets/<id>/actions \
  -H "content-type: application/json" -H "x-actor: priya.sharma@netlink.com" \
  -d '{"action":"assign","assigneeId":"user_arjun"}'

# health + active feature flags
curl -s http://localhost:3000/api/v1/health

Note In production mode (DEMO_MODE=false) the x-actor header is disabled; use a session cookie or an API key (Authorization: Bearer nlk_…). The full surface is documented at /api/v1/openapi.json.
